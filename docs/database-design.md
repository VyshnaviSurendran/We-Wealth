# Database Design

All tables use a UUID primary key (`id`). Timestamps (`created_at`,
`updated_at`) are added via a shared mixin except where noted.

| Table | Key fields | Notes |
|---|---|---|
| `users` | name, email (unique), phone, password_hash, is_active | |
| `households` | name, created_by → users, currency, timezone | |
| `household_members` | household_id, user_id, role (`OWNER`/`MEMBER`), status (`INVITED`/`ACTIVE`/`REMOVED`), joined_at | no timestamps mixin |
| `household_invitations` | household_id, email, invited_by → users, status | tracks pending partner invites |
| `categories` | household_id, name, category_type (`EXPENSE`/`INCOME`), is_shared, is_active | seeded with defaults on household creation |
| `accounts` | household_id, owner_user_id, name, account_type, opening_balance, is_shared, is_active | `current_balance` is **not** stored — always computed (see `balance_service.py`) |
| `incomes` | household_id, account_id, owner_user_id, category_id, title, amount, income_date, status (`EXPECTED`/`RECEIVED`/`CANCELLED`), visibility, created_by | |
| `expenses` | household_id, account_id, paid_by_user_id, category_id, title, amount, expense_date, due_date, status (`PENDING`/`PAID`/`CANCELLED`), visibility, created_by | |
| `transfers` | household_id, from_account_id, to_account_id, amount, transfer_date, created_by | CHECK: accounts differ, amount > 0 |
| `savings_goals` | household_id, owner_user_id, name, target_amount, current_amount, target_date, visibility, status | |
| `budgets` | household_id, owner_user_id, category_id, amount, period_type, start_date, end_date, visibility | |
| `recurring_bills` | household_id, account_id, category_id, title, amount, frequency, next_due_date, status, visibility | |

## Why balances aren't stored

`Account.current_balance` is intentionally omitted as a column. Storing it
alongside the transactional rows (incomes/expenses/transfers) risks drift if
any write path forgets to update it. `balance_service.py` computes actual /
pending / safe-available balance from the underlying rows on every read.
For this app's expected data volume this is fast enough; if it ever becomes a
bottleneck, a cached `current_balance` column maintained by a service-layer
transaction is the natural next step — see the note in the original plan
(section 4.4).

## Migrations

The initial schema is defined by hand in
`backend/alembic/versions/0001_initial_schema.py` (not autogenerated — no
live Postgres instance was available in this environment to diff against).
Verify it against a real database with `alembic upgrade head` before relying
on it, and use `alembic revision --autogenerate` for all schema changes from
here on.
